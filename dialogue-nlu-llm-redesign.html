0结论摘要

方案整体成立：解析侧架构（自定 nlu_10 协议 + 固定薄 parser + 全候选严格门 + 不发布部分语义）正是自控格式场景下的推荐落法，与 llama.cpp 的兼容性也良好。但它有一个系统性偏差——把全部鲁棒性押在“事后解析”上，而“事前约束”完全缺席。重构的核心只有一句话：

事前语法约束（json_schema → GBNF）消灭格式失败，事后只留语义校验；每个失败都有定义好的出口（有界重试 → 兜底）；易变参数收进 Profile，协议保持冻结；思考行为显式受控。

原方案中“错误或不合适”的部分共 8 项，逐条详解见第 1 节；重构后的管线、失败出口、配置模型见第 2–4 节；可分五步落地、每步独立可回滚，见第 6 节。

1问题清单（必须改 / 建议改，逐条详解）

图 1 · V3 配置方案问题地图（P0/P1/P2 分级 + 保留项）

P0-1生成侧约束缺失 —— 最重要的一个问题

你的现状：BuildRequest 的固定 JSON 只含 model / messages / temperature / top_p / top_k / max_tokens / stream:false，没有 response_format。全部格式鲁棒性由 ParseResponse 承担：精确 descriptor marker 匹配 + 全候选通过才发布。

为什么这不合适：LLM 的输出本质是从分布里采样，prompt 对输出格式只是软约束；0.6B 级模型再经 Q4/Q6 量化，指令跟随能力进一步下降——marker 漂移是统计必然，不是偶发事故。事后严格解析只能“拒绝坏输出”，永远不能“阻止坏输出”。这与 llama.cpp autoparser 的教训一致：连 llama.cpp 自己都要靠十几个家族的白名单 workaround 兜底，事后解析永远在和模型漂移博弈。而 llama.cpp 恰好是做事前约束最方便的引擎：请求加 response_format: {"type":"json_schema","json_schema":{...}}，llama-server 内部把 schema 编译为 GBNF grammar，每一步 token 采样都被限制在合法语法内，语法失败概率趋近于 0。

不改会发生什么：间歇性 marker miss → 候选全灭 → unknown 兜底率随模型版本 / 量化版本漂移上升；且你无法区分“模型能力不足”与“协议设计缺陷”，排障只能人肉翻 bad case，每次换 GGUF 都要重新回归。

修正方案：HTTP 路径请求体加 response_format；offline 路径在 common_chat_templates_apply 的 inputs 里传 json_schema，返回的 common_chat_params.grammar 注入采样器。建议 grammar 直接覆盖「marker 行 + JSON 体」——nlu_10 协议本身完全不用改，marker 也纳入语法约束。将来若想切纯 JSON 协议，走你们 TODO 里预留的 codec + factory 显式新增（nlu_11），别悄悄改。

边界认识（重要）：grammar 只保语法不保语义——{"intent":"weather","slots":{"city":""}} 是 schema 合法的，但仍可能过不了你们的槽位校验。语法失败被消灭后，语义级失败仍在，这正是 P1-1 失败出口的存在空间。

如何验证：上线前后对比 marker-miss 计数，预期下降 1–2 个数量级；ParseResponse 的严格门保留，但从“防线”降格为“形式校验”。

P0-2thinking 行为未定义 —— 会直接打破 marker 匹配

你的现状：BuildRequest 明确“无 thinking-control 字段”（你们的端点也禁止传入 thinking 字段——这个约束本身没问题）。

为什么这不合适：Qwen3-0.6B 是混合思考模型，GGUF 里的官方模板默认 enable_thinking=true：模型会先输出一段 <think>…</think> 再进正文。后果有三层：① descriptor marker 前面垫着几百 token 的思考文本，marker 匹配偏移甚至匹配不到；② 思考段先消耗 max_tokens 预算，正文可能被截断在半截 JSON 上；③ 车机 1.5–2s 延迟预算被思考段吃掉一大块。

修正方案（按你们的端点约束适配，不加请求字段）：分阶段三层——

  • L2（立即可用）：在 system / user 消息末尾追加 /no_think。这是 Qwen3 家族的软开关，走 --jinja + GGUF 原生模板即可生效，不需要任何 API 字段；
  • L4（训练季，终态）：nlu_10 LoRA SFT 数据不含 think 段、用与线上同一模板渲染——模型母语就是非思考输出，运行时零依赖；
  • S0（常驻兜底）：ParseResponse 前置剥离 <think>…</think>，并入 V3 既有清洗步骤。注意要处理未闭合情形（生成流被 max_tokens 截断时只有开头 <think>）——此时剥到文本末尾并计入失败分类。

如何验证：S0 剥离命中率应随 L2 生效降至 ≈0；若居高不下，说明当前量化版本的模型没有遵循 /no_think，需检查模板是否走了 --jinja 路径。提醒：/no_think 是 Qwen3 家族特性，将来换 Qwen3.5+ 或其他家族需复核（届时以 L4 为准）。

P0-3双路径渲染一致性未规定 —— “只在某平台复现”的排障地狱

你的现状：Linux=HTTP（OpenAI endpoint）、Android=offline（inference hook）复用同一 JSON——这是对的；但方案没有规定两条路径用哪个模板引擎渲染。

为什么这不合适：llama.cpp 有两条模板路径：legacy（llama-chat.cpp 内置命名模板枚举 + 启发式指纹猜测）与 --jinja（执行 GGUF tokenizer.chat_template 里模型作者写的 Jinja）。不开 --jinja（或 API 侧 use_jinja=true）时启发式可能误选；两个平台若一个走 legacy、一个走 jinja，渲染结果字节级不同（空白、消息头格式差异），模型看到的分布不同，marker 就会在一个平台稳定、另一个平台偶发 miss——这种跨平台不对称故障在现场几乎无法定位。

修正方案：两侧统一 use_jinja=true；模板唯一事实源 = GGUF 元数据（与权重同文件、同版本、一起 OTA）；NluConfig 里不要放模板字符串的第二份拷贝——第二份必然漂移。这条还直接影响 P0-2：legacy 路径不支持模板变量，/no_think 的可靠性依赖 jinja 路径。

如何验证：用同一组 messages 在 Linux / Android 两路径分别渲染，diff 结果应字节级一致（可做成一条 CI 用例）。

P1-1失败出口未定义 —— “全候选不通过”之后系统去哪

你的现状：“全部候选通过后才发布”定义了成功路径，但它的反路径——全都不通过时系统去向——是未定义状态（隐含直接 unknown 兜底）。

为什么不合适：grammar 落地后语法失败≈0，但语义级失败（槽位为空、值不合法、候选风格不匹配）仍会发生。失败有两种成因：采样噪声（带反馈重采样即可修复）与系统性问题（prompt 歧义、schema 缺陷、模型能力不足）。直接兜底无法区分两者，等于把一次免费的成功机会和一条健康告警一起扔掉。

修正方案：有界重试阶梯（详见第 3 节与图 3）：失败分类先行（只有格式/校验失败可重试，超时/取消/5xx 直接兜底）→ 预算守卫（elapsed < T_total/2）→ retry ×1（原 messages + 失败原因反馈 + temperature ↓）→ 仍败 → unknown → DM。两次尝试封闭在 NluLlmManager 内部，对外仍是 1 个逻辑请求——这是与你们 NLU 网关幂等/并发主线的直接对接点：失败尝试若泄漏到历史层，重试成功后历史里就有脏记录。

P1-2采样参数耦合进共享协议 —— 换模型 = 改代码发版

你的现状：temperature / top_p / top_k / max_tokens 写死在共享的 BuildRequest 固定 JSON 里。

为什么不合适：这四个值是模型相关参数，不是协议：Qwen3-0.6B 的 Q4 与 Q6 需要的温度不同，换云端模型更是完全不同。写死在共享代码里，每次换模型/量化版本都要改代码发版。另外两点常被忽视：① NLU 是决策型输出（intent+slots），不是闲聊——聊天取向的默认温度（0.7 一类）在这里不合适，建议 temperature ≤ 0.2；② max_tokens 是预算杠杆（think 关闭后可以收紧，直接省延迟），与采样质量杠杆应分开管理。

修正方案：四个参数全部移入 Profile 下发（你们 NluConfig→Model→Profile 分层已预留位置）；BuildRequest 的 JSON schema 保持冻结——稳定的进协议，易变的进配置。配套：grammar 落地后 n=1 起步（见 P2-2）。

P1-3墙钟预算与 barge-in 取消未定义

你的现状：stream:false 意味着只有 max_tokens 这个 token 数上界，没有墙钟时间上界；用户抢话打断（barge-in）时请求的取消行为也未定义。

为什么不合适：车机语音交互的延迟预算是硬约束（用户在等）。超时说明预算已耗尽，此时重试只会更糟；取消说明用户已放弃，继续生成浪费电量和算力（端侧 0.6B 跑在 SoC 上尤其敏感）。

修正方案：定义 T_total 墙钟预算（Runtime 层配置）；超时/取消 propagates 到引擎侧停止采样；取消与超时一律不进 retry，直接收口。这与 P1-1 的失败分类是同一条规则的三个分支。

P2-1可观测性缺口

方案没有任何运行指标。建议最小集：四类失败分类计数（marker_miss / schema_fail / semantic_fail / timeout）、S0 剥离命中率（= /no_think 是否仍然生效的探针）、retry-rate（grammar 生效后应≈0，爬升说明该修 prompt/schema 而不是 parser）。车规 OTA 场景下，这些计数是配置和代码之外唯一的问题定位线索——没有它们，现场问题只能靠复现。

P2-2多候选成本未评估

“全候选通过才发布”逻辑正确，但注意成本：n 个候选 = n 次完整生成，延迟线性放大。grammar 落地前多候选是对漂移的补偿；落地后语义分歧概率大降，n=1 大概率足够。建议：grammar 上线前保留小 n，上线后切 n=1 并观察 semantic_fail 计数，把候选裁决保留为校验手段而非采样策略。

3失败出口与有界重试

图 3 · 失败出口状态机（分类 → 守卫 → 单次反馈重试 → 兜底）
规则内容理由
1 · 失败分类先行只有「格式/校验失败」可重试；超时/取消/5xx 直接兜底超时 = 预算已尽，重试更糟；取消 = 用户已放弃
2 · 预算守卫elapsed < T_total / 2 才允许 retry防「首次耗尽预算 + 重试再超时」双重惩罚，延迟上界恒为 2× 单次
3 · 反馈式重试原 messages 原样保留 + 追加失败原因 + temperature ↓LLM 自我修正依赖错误信息，盲重采样成功率远低于带反馈重试
4 · 幂等边界两次尝试封闭在 Manager 内，对外 1 个逻辑请求；失败尝试不写历史与网关 QueryGuard / 会话幂等控制对齐，防止历史层脏记录
5 · 健康探针retry-rate 上报，grammar 生效后应 ≈ 0带反馈仍失败 = 系统性信号（修 prompt/schema，而非加重试）

为什么是 ×1 而不是 ×N：带反馈仍失败意味着第三次成功率趋近零——×1 是区分「采样噪声」与「系统性失败」的最小实验；延迟上界 2× 可预算；端侧每次 retry 是完整重生成（反馈消息改变了后缀，前缀 KV 复用省不了多少）。

4.2 NluConfig 目标形态

nlu_llm:
  protocol: nlu_10                # 冻结：messages schema + markers + 输出 schema
  model:
    id: qwen3-0.6b
    quant: Q6_K                   # 结构化输出对量化敏感：建议 Q6/Q8 起步
    gguf: models/qwen3-0.6b-q6_k.gguf
    sha256: 7f3a...               # 权重+模板同版本锁定（模板内嵌 GGUF，无第二份）

    default:
      temperature: 0.1            # 决策型输出：低温
      top_p: 0.8
      top_k: 20
      max_tokens: 256             # think 关闭后可收紧（预算杠杆）
      response_schema: nlu_10     # 生成侧约束（HTTP 与 offline 均生效）
      thinking: no_think_suffix   # L2；SFT 后切换为 baked
      candidates: 1               # grammar 落地后 n=1 起步
  runtime:
    linux:
      endpoint: http://127.0.0.1:8080/v1/chat/completions
      use_jinja: true             # 与 Android 保持同一渲染
    android:
      lib: libnlu_offline.so
      use_jinja: true
    budget_ms: 2000               # T_total 墙钟
    retry:
      max: 1
      guard: half_budget
      feedback: true

7原设计中应保留的部分（明确肯定）

  • stream:false + bounded buffer + 不发布部分语义 —— NLU 输出是决策不是展示，半截槽位发布是事故（"city":"北" 就去查天气）。流式机制 llama.cpp 现成（is_partial + compute_diffs），延后成本低，是期权不是欠债；
  • 全候选严格门 —— 逻辑正确；grammar 落地后自动降格为形式校验，无需删除；
  • codec + 显式 factory case 的 TODO 边界 —— Rule of Three：样本量为 1 时不做抽象；显式枚举让协议变更有代码轨迹，车规审计需要；运行时可插拔协议框架 = 重造 autoparser，明确不做；
  • offline / online 复用同一 JSON —— 双路径一致性的基础，只需再补「同一模板引擎」这一条；
  • NluConfig → Model → Profile 分层 —— 方向正确，本方案只是把字段归属进一步明确（第 4.1 节）。
