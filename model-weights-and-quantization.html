1. 模型权重：从参数到字节

权重就是训练学到的参数张量。一个 Transformer 的权重 = 每层的 4 个注意力投影矩阵（Wq/Wk/Wv/Wo）+ 3 个 FFN 矩阵（gate/up/down）+ 归一化向量 + Embedding 表（与输出层可共享）。推理阶段权重只读不更新——这是它能被离线量化的根本原因。

1.1 参数量怎么算（以 Qwen3-0.6B 为例）

config.json 的每个字段都直接映射到参数量。Qwen3-0.6B：hidden_size=1024、num_hidden_layers=28、16 query 头 / 8 KV 头（GQA）、head_dim=128、intermediate_size=3072、vocab_size=151,936、tie_word_embeddings=true。

组件计算参数量占比
Attention（每层）Wq 1024×2048 + Wk/Wv 2×1024×1024 + Wo 2048×10246.29M×28 层
FFN（每层）gate/up/down 3×1024×30729.44M
Norms（每层）2×RMSNorm + QK-Norm2.3K
Embedding（tied）151,936 × 1024（输入输出共享一份）155.6M26.1%
总计596,049,920100%
小模型特有现象：Embedding 占 26%（同词表在 8B 模型里只占 ~4%）。词表成本是固定的，不随模型缩放——所以 0.6B 量化时 embedding 张量常被单独保留更高精度（部分量化工具默认如此），它是"性价比最高的一块保护"。

1.2 数值格式：位分配决定「动态范围 vs 精度」

图 1 · 参数构成、数值格式位分配与各量化格式大小（Qwen3-0.6B 实例）

浮点数由符号位 + 指数 + 尾数构成：指数位数决定动态范围（能表示多大/多小的数），尾数位数决定精度（格点密不密）。

  • FP32：训练默认，4 字节，推理浪费；
  • FP16 vs BF16：都是 2 字节，但 FP16 是「e5m10」（范围窄 ±65504、精度高），BF16 是「e8m7」（范围同 FP32、精度低 8 倍）。LLM 训练/推理选 BF16 是因为激活值范围大，BF16 溢出风险小——这也是后面 outlier 问题的伏笔；
  • FP8（E4M3/E5M2）：把浮点压到 1 字节，Hopper/Blackwell GPU 硬件原生支持，是「不改数值含义的量化」；
  • INT8/INT4：整数格点是均匀的，浮点是非均匀的（小数附近密、大数附近疏）。整数量化必须做线性映射（scale/zero-point），这是第 2 章的主题。

1.3 大小测算公式（部署前必算）

文件大小   ≈ 参数量 × bpw ÷ 8              （bpw = bits per weight，见下表）
运行内存   = 权重 + KV cache + 运行时开销(10~20%)
KV cache  ≈ 2 × 层数 × KV头数 × head_dim × 每token字节数 × 上下文长度
             Qwen3-0.6B: 2×28×8×128×2B ≈ 112KB/token → 4K 上下文 ≈ 448MB
经验法则：车机 4K 上下文时，0.6B 的 KV cache（448MB）可能比 Q4_K_M 权重本体（0.37GB）还大。只盯权重大小会踩坑——上下文长度和 KV 量化（--cache-type-k q8_0）同样是内存杠杆。

2. 量化原理：线性映射、粒度、误差

图 2 · 仿射量化、对称/非对称、三种粒度、两类误差、三档量化对象

2.1 仿射量化：一条公式讲完全部

量化    q = round(x / s) + z          INT4 时 q ∈ [−8, +7]，仅 16 个格点
反量化  x̂ = (q − z) × s               s = (x_max − x_min)/(q_max − q_min)

整数量化 = 把连续的浮点权重吸附到有限个均匀格点上。单权重误差上界 |x − x̂| ≤ s/2：步长越小越准，但可表示范围越窄。所有量化格式的差异，本质上都是「怎么分组定 s（粒度）+ 怎么补偿误差（方法）」。

  • 对称量化（z=0）：适合近似对称分布的权重；
  • 非对称量化（z≠0）：适合偏移分布（ReLU 后激活全为正）。

2.2 粒度：scale 共享多少权重

粒度scale 数量特点典型用途
per-tensor每矩阵 1 组元数据最省、误差最大早期 W8
per-channel每输出通道 1 组（数百~数千）主流平衡点W8/AWQ/GPTQ
per-group每 32/256 个权重 1 组误差最小；scale 本身再用 6bit 压缩（k-quant super-block），抵消元数据膨胀GGUF k-quants（端侧 4bit 的可行性基础）

这是 llama.cpp 能把 4bit 做到可用的关键：Q4_K_M 名义 4bit，实际 ~4.89 bpw——多出来的 0.89 bit 就是分组 scale 的开销，换来的是精度大幅回升。

2.3 误差从哪来

  • round-off（舍入噪声）：每权重 ±s/2 的均匀噪声，单看微小，经 28 层矩阵乘累积放大，最终表现为 logits 抖动、近并列 token 翻转（top-1 改变）——对你们 nlu_10 这种严格格式输出，这正是 marker 偶发 miss 的微观机制，grammar 约束是兜底，量化选型是源头；
  • outlier（主要矛盾）：LLM 激活存在系统性离群通道（少数维度数值比其他大 100 倍）。若按 max 定 s，99% 的普通值被挤进极窄格点 → 误差暴涨。GPTQ/AWQ/SmoothQuant 三大方法全为解决它而生。

2.4 量化对象三档

档位记法谁被量化收益与代价
权重-onlyW4A16 / W8A16权重（静态、可离线）内存/带宽省；激活仍浮点。llama.cpp 全家在此档
权重+激活W8A8两者都要量化GPU 整数 kernel 端到端加速；激活是动态的 → 难点在 outlier（SmoothQuant）
KV cacheq8_0 KV注意力缓存上下文内存减半，长上下文收益最大；质量影响通常很小

3. 量化方法全景

图 3 · PTQ（训练后量化）与训练侧方法全景
方法比特/对象需要校准集？一句话原理适用
RTN任意 / W否朴素取整，零成本基线8bit 够用；4bit 损伤大
GPTQ4~8 / W是（128~512 条）逐层用 Hessian 二阶信息求解「量化哪个权重的误差最小」，边量化边补偿GPU 生态 4bit 主流

k-quants / IQ2~8 / W可选（imatrix）super-block 分组 + 6bit scale；IQ 系列用重要性矩阵分配比特llama.cpp / 端侧（你们的主路径）
SmoothQuantW8A8是把激活 outlier 数学等价地迁移到权重，让 W/A 双方能整数量化GPU serving
FP8 (E4M3)8 / W+A轻浮点 8bit 保留动态范围，硬件原生，无需整数映射技巧TRT-LLM / vLLM（Hopper+）

共同思想：量化误差代价集中在「少数重要通道」——GPTQ 用二阶信息找补偿方向，AWQ 用激活幅度找重要列，imatrix 用领域数据统计重要性。校准集越贴近真实分布，量化越准——这就是为什么第 4 章坚持用你们 NLU 领域 query 做校准。

4. 如何量化：实操流程（llama.cpp 路线）

四步流水线：转换 → 校准（可选） → 量化 → 验证。全部命令在 llama.cpp 构建目录执行。

4.1 转换：HF 权重 → GGUF

python convert_hf_to_gguf.py /path/Qwen3-0.6B \
    --outfile qwen3-06b-f16.gguf --outtype f16

GGUF = 权重 + tokenizer + 架构元数据 + 模板单文件分发（前面聊 chat-template 时说的「单一事实源」就是这里的 tokenizer.chat_template 元数据键）。先转 F16 作为量化母本。

4.2 校准：生成重要性矩阵（imatrix）

./llama-imatrix -m qwen3-06b-f16.gguf -f nlu_calib.txt -o imatrix.dat

nlu_calib.txt 是普通文本文件，放领域语料——你们的真实/合成 NLU query、车控指令、多轮对话转写，几百 KB 即可。imatrix 统计每个张量上激活的分布，量化时据此保护重要权重。跳过这步用默认 RTN 也能量化，但 0.6B 级小模型建议总是带 imatrix。

4.3 量化

./llama-quantize --imatrix imatrix.dat \
    qwen3-06b-f16.gguf qwen3-06b-q4km.gguf Q4_K_M
./llama-quantize qwen3-06b-f16.gguf qwen3-06b-q8.gguf Q8_0

一条命令一个格式。产出多个候选（Q8_0 / Q6_K / Q5_K_M / Q4_K_M）供第 5 章的评测对比。

4.4 运行时配套开关

./llama-server -m qwen3-06b-q4km.gguf \
    --jinja \                          # 用 GGUF 内嵌 Jinja 模板（单一事实源）
    --cache-type-k q8_0 \              # KV cache 量化：上下文内存减半
    --cache-type-v q8_0 \
    -c 4096                            # 上下文长度（KV 预算的一部分）

4.5 其他路线速览

  • GPU serving（TRT-LLM）：走 FP8/NVFP4 checkpoint 量化（ModelOpt/AMMO 工具产出），与 llama.cpp 路线互不干扰；车机端侧用不到，云端节点可参考；
  • 训练侧（LLaMA-Factory）：QLoRA（NF4 底座 + LoRA 微调 nlu_10）——注意这产出的 LoRA 适配器在合并导出后再走 4.1 的 GGUF 转换，两条链路衔接。

5. 如何评价模型效果：四维度 + 方法论

图 4 · 评价体系：② 任务效果是门槛，①③④ 是约束

5.1 量化保真（离原版多近）——工具现成

./llama-perplexity -m qwen3-06b-q4km.gguf -f wikitext-2-raw.test.txt   # 通用 PPL
./llama-perplexity -m qwen3-06b-q4km.gguf -f nlu_domain.txt            # 领域 PPL
./llama-bench -m qwen3-06b-q8.gguf qwen3-06b-q4km.gguf -p 512 -n 128  # 性能对比
指标含义经验判读
ΔPPL（困惑度增幅）模型对文本的「意外程度」，越低越好≤5% 安全；5~10% 观察；>10% 通常可感知
logit 翻转率同输入下 top-1 改变的 token 比例（需 Python 侧对比）直接对应格式漂移风险，nlu_10 场景建议测
生成一致性greedy + 固定 seed 下逐 token diff 比例task 集上 diff > 20% 说明量化已伤及输出分布

5.2 任务效果（最重要——业务口径）

通用 benchmark（MMLU / C-Eval / GSM8K）对 0.6B 接近随机基线，分数噪声大，只作参考；真正的门槛是你们自己的 NLU 任务集：

  • intent 准确率 / slot F1：标注集 = 真实 query + 合成 query（覆盖长尾 intent 切片）；
  • 格式遵守率：marker 命中率 + JSON schema 校验通过率——这是量化对你们最直接的风险面（logit 抖动 → marker 漂移）；
  • 端到端多轮对话成功率：含纠错、追问、barge-in 路径。

5.4 方法论红线（不守住则全部数字无效）

  • greedy + 固定 seed 才可对比——temperature>0 的 A/B 是抽签；
  • 回归集 ≥500 条，含长尾 intent 切片——总量指标会掩盖切片塌陷；
  • 同模板/prompt/上下文——量化前后只变量化格式这一个因子（注意前几轮定的 /no_think 后缀和 --jinja 保持一致）；
  • 基准锚定 Q8_0 而非 BF16——Q8_0 ≈ 无损且可用，直接对比 F16 会把「量化损失」和「部署损失」混在一起。

6. 落地建议：0.6B 车机 NLU 的量化选型

图 5 · 量化选型决策流：预算 → 基线 → 候选 → 回退 → 换模型

6.1 0.6B 的量化特殊性

  • 小模型对量化更敏感：参数越少，每个权重承载的信息密度越高、层内冗余越少——同一位宽下 0.6B 的相对损失大于 7B+。社区经验：大模型 Q4_K_M 近无损，小模型要上移到 Q6/Q8；
  • Embedding 占 26%：量化工具默认对 embedding/output 保留较高精度（Q6_K），这一块不用操心但要知道；
  • 「大模型 + 低位宽 > 小模型 + 低位宽」：1.7B 的 Q4_K_M 通常优于 0.6B 的 Q3_K_M——内存预算允许时，别用降位宽省内存，用换大一号模型花内存；
  • KV cache 是被忽视的杠杆：4K 上下文时 KV（448MB）> Q4 权重（0.37GB），--cache-type-k/v q8_0 先于降权重量化考虑。

6.2 建议路径

  1. 按第 4 章流程产出 Q8_0 / Q6_K / Q5_K_M / Q4_K_M（全部带 imatrix 领域校准）四个候选；
  2. 跑第 5 章评测门槛表，Q4_K_M 过门槛就用它（0.37GB，OTA 包体友好）；过不了上 Q5/Q6（0.43/0.49GB，车机通常装得下）；
  3. 进入 nlu_10 LoRA SFT 之后重跑一遍评测——SFT 会改变输出分布（更集中在格式化输出上），量化敏感面随之变化；
  4. 线上灰度监控「格式遵守率」作为量化健康指标，与前面 retry-rate 探针同一套观测面板。
一句话总结：权重是只读参数张量，量化是「分组线性映射 + 误差补偿」，0.6B 场景的方法选 k-quants+imatrix，评测锚定 Q8_0 基线上的任务指标切片而非通用 benchmark——内存不够先砍 KV 和上下文，再考虑降位宽，最后才考虑换模型大小。
