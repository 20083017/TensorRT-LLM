nlu_10 Schema 调优设计方案

日期：2026-10-27 · 适用：WTP184 dialogue V3 NLU-LLM 链路 · 配套文档：dialogue-nlu-llm-redesign.html（管线与失败出口）、model-weights-and-quantization.html（量化与评测门槛）

1. 结论（先读这页）

三句话结论：
① Schema 调优可行且是 0.6B 场景 ROI 最高的工程杠杆——把输出任务降到模型能力射程内，格式遵守率可从 ~95% 拉到 ~99.5%，改配置即可验证，天级迭代。
② 它只治「表达失败」（知道答案但输出格式错），不治「判断失败」（intent 本身判错）——后者是 nlu_10 LoRA SFT 的职责。
③ 铁律：schema 必须先定稿、再生产 SFT 数据——SFT 数据按协议渲染，协议一变数据作废。顺序：先工程杠杆，后模型杠杆。

2. 两条失败轴与能力边界

retry-rate 健康面板上爬升的失败，先分成两轴再决定治法——这是本方案全部策略的分诊台：

失败轴现象根因治法量级预期
表达失败marker miss / JSON 残缺 / 字段错位 / 枚举外取值 / 缺槽表达混乱输出格式超出模型稳定能力（0.6B + 量化 + 采样）本方案：schema 调优 + grammar + few-shot格式遵守率 95% → 99.5%
判断失败格式完全合法，但 intent 判错 / 槽位内容错模型语义理解天花板（0.6B 蒸馏模型）nlu_10 格式 LoRA SFT（领域 query 对 × 数千）intent acc / slot F1 的提升来源
边界诚实声明：schema 调优拉满之后剩余的失败 ≈ 判断失败。若分桶显示「格式合法但内容错」占比高，停止继续打磨 schema，转投 SFT。

3. 七条设计原则

#原则原理
1intent 封闭枚举选择题优于填空题：枚举 + grammar 后模型在 N 个候选里选，不在 15 万词表里自由生成
2flatten，深度 ≤1每层嵌套都是 0.6B 的出错点；字段序固定，intent 永远在前（先做最高置信的决策）
3字段名语义化字段名是 prompt 的一部分：city 自带语义提示，slot_01 没有
4absence 语义全库统一槽位缺失只有一种表达（空串），不留给模型「空串 / null / 省略」三选一
5弃 number 类型数字 token 化易错位（"23.5" 切成多 token）；改字符串 + 枚举粒度（low/mid/high）
6输出窗口贴近最短合法输出max_tokens 每多一个 token 就多一个出错窗口；grammar 逐字段收紧后多余文本物理不可能出现
7自由文本槽 → 受控词表city 这类槽位改受控词表 + other 兜底，与枚举同理；词表本身就是校验规则

4. nlu_10 v2 Schema 设计

图 1 · v1（嵌套 + 自由生成）→ v2（扁平 + 封闭枚举）：五个问题与五个修正一一对应

v2 完整定义（JSON Schema，propertyOrder 为本方案自定义扩展，供 grammar 生成器确定字段序）：

{
  "type": "object",
  "propertyOrder": ["intent", "city", "date", "temp_level"],
  "properties": {
    "intent":     { "type": "string",
                    "enum": ["hvac_on","hvac_off","hvac_temp_up","hvac_temp_down",
                             "nav_go","music_play","weather_query","unknown"] },
    "city":       { "type": "string" },
    "date":       { "type": "string",
                    "enum": ["today","tomorrow","monday","tuesday","wednesday",
                             "thursday","friday","saturday","sunday",""] },
    "temp_level": { "type": "string", "enum": ["low","mid","high",""] }
  },
  "required": ["intent","city","date","temp_level"],
  "additionalProperties": false
}
字段类型取值缺失表达设计说明
intent封闭枚举全量 intent 列表（含 unknown 兜底）必填决策输出放最前；unknown 是对抗输入的合法出口
city受控词表城市词表空串词表随 Profile 下发；不自由生成
date枚举today / tomorrow / monday..sunday空串不用日期数字——绝对日期解析交给规则后处理
temp_level枚举low / mid / high空串替代 number 温度：枚举粒度够用且 token 稳定

三条删除决定（v1 → v2）：删 confidence（0.6B 校准极差，无决策价值——置信度由 L3 校验 + retry-rate 面板承担）；删 slots 嵌套层（深度 2 → 1）；删 number 类型（全部字符串化）。每条删除都对应一类失败指纹的消除。

5. 三位一体：schema = grammar = 校验

图 2 · 单一事实源派生三个产物，变更同步传播、编译期暴露不同步

三个产物同源派生，实现路径：

  • ① GBNF grammar（生成侧约束，L0）：HTTP 路径用 response_format: json_schema（llama-server 原生，内部转 grammar）；offline 路径把 schema 交给模板 inputs，取 common_chat_params.grammar 注入采样。枚举直接编译为字面量交替规则，字段序编译为固定序列——grammar 能强制字段顺序，这是「字段序固定」原则可执行的原因。
  • ② Validator（L3 候选门）：enum / absence / 字段序校验规则从同一 schema 生成，不手写第二份。
  • ③ Codec + factory case：解析代码的枚举与 schema 同源（codegen 或编译期断言），协议变更走显式 factory case + code review——车规审计需要代码轨迹。
GBNF 片段（示意，由 schema 生成）：
root   ::= "{" ws "\"intent\":" ws intent "," ws "\"city\":" ws string
           "," ws "\"date\":" ws date "," ws "\"temp_level\":" ws tl "}"
intent ::= "\"hvac_on\"" | "\"hvac_off\"" | ... | "\"unknown\""
date   ::= "\"today\"" | "\"tomorrow\"" | ... | "\"\""
tl     ::= "\"low\"" | "\"mid\"" | "\"high\"" | "\"\""

6. Prompt 配套设计

schema 定「输出什么」，prompt 定「怎么引出」。三条规则：

  • few-shot 补边界对：每对近义 intent 的最小对立句式各给一个正例（「放首歌」→ music_play，「打开音乐APP」→ app_open）。边界对是 intent 互串最有效的疫苗；只用正例——小模型容易被反例带偏。
  • 指令单一、祈使、短：一个 prompt 只问一件事，规则写在 system，示例紧跟规则。
  • 上下文结构化：location / app status 等服务端上下文放 system 的固定格式段落，不混进自然语言叙事。
System 模板骨架：
你是车载 NLU 引擎。只输出一行 JSON，不要输出任何其他文字。
字段固定顺序：intent, city, date, temp_level。
intent 取值：hvac_on / hvac_off / hvac_temp_up / hvac_temp_down
             / nav_go / music_play / weather_query / unknown
date 取值：today / tomorrow / monday..sunday / 空串
temp_level 取值：low / mid / high / 空串
槽位没有提到就输出空字符串 ""。
[服务端上下文] 位置：xx市 · 当前应用：导航
Examples:
用户：打开空调          → {"intent":"hvac_on","city":"","date":"","temp_level":""}
用户：明天去上海        → {"intent":"nav_go","city":"上海","date":"tomorrow","temp_level":""}
用户：放首歌            → {"intent":"music_play","city":"","date":"","temp_level":""}
用户：打开音乐APP       → {"intent":"app_open","city":"","date":"","temp_level":""}   ← 边界对
用户：今天天气怎么样    → {"intent":"weather_query","city":"xx市","date":"today","temp_level":""}

7. 失败指纹 → 修正策略映射

调优不是拍脑袋改，是失败指纹驱动——每类线上/评测失败指向特定设计缺陷：

失败指纹schema / prompt 修正
空 slot / 缺失表达混乱absence 语义统一（空串）+ few-shot 补「槽位缺失」正例
近义 intent 互串枚举间距拉开或合并近义项；few-shot 补边界对（同句式两意图各一例）
字段错位 / 嵌套混乱flatten 深度 ≤1；字段序固定（intent 在前）；字段名语义化
夹带额外文本 / 输出超长max_tokens 贴近最短合法输出；grammar 逐字段收紧；自由文本槽改受控词表
数字 / 日期槽出错弃 number；改字符串 + 枚举粒度
多意图压成单 intent协议写明「取主意图」规则 + few-shot 演示；或两阶段拆分（§9）

8. 调优闭环与评测集构建

8.1 评测集构成

切片构成占比建议
主干真实线上 query 抽样 + 人工标注60%
边界对每对近义 intent 的最小对立句对，全 pair 覆盖15%
槽位缺失隐含槽位 / 槽位不全的 query10%
长尾方言、ASR 噪声（同音字替换）、多意图句10%
对抗指令外闲聊 / 无关输入（应回 unknown）5%

规模：每意图 ≥50 条，总量 1000–3000 条；固定 seed、git 版本化（评测集本身是资产，改集 = 改基线，必须走 review）。

8.2 测法与门槛

所有 A/B 用 greedy + 固定 seed（隔离采样噪声，只看设计变量）；量化选型对比时锚定 Q8_0 而非 F16。门槛承接量化文档第 5 章：

指标门槛测法
格式遵守率≥ 99.5%grammar 开启下，解析 + 校验通过的占比
intent accuracy相对 Q8_0 基线降幅 ≤ 1pp评测集 greedy
slot F1降幅 ≤ 2pp同上
长尾切片 acc降幅 ≤ 5pp分桶统计（防均值掩盖尾部）
retry-rate（线上）≈ 0（< 0.5%）与格式遵守率同面板观测

9. 两阶段拆分实验（P1）

项内容
设计Stage 1 只输出 intent（grammar 只约束 intent 枚举，输出 ~10 token）；Stage 2 按 Stage 1 结果选该 intent 的子 schema，只输出其槽位字段
假设每步输出更短 → 格式率↑；Stage 2 不再面对全枚举 → 近义干扰↓
度量端到端 intent acc / slot F1 / 端到端 P50 延迟（2× 单步预算内？前缀 KV 复用可省一半 prefill）
决策规则intent acc 提升 ≥ 1.5pp 且延迟仍在预算内 → 采纳；否则保持单阶段
成本两份 few-shot 维护 + 请求构造 ×2；用失败分桶数据先验证假设再投入

10. 与 SFT 的分工与顺序

维度schema 调优（工程杠杆）nlu_10 LoRA SFT（模型杠杆）
改什么输出协议的难度模型权重的领域适配
提升什么格式遵守率 95 → 99.5%intent acc / slot F1（判断失败轴）
迭代成本改配置 + 重测，天级数据生产 + 训练 + 量化重评测，周级
前置依赖无（可立即开始）schema 定稿——SFT 数据按协议渲染，协议变则数据作废
附带收益grammar / validator / codec 同源thinking 烧死（L4 终态）、/no_think 依赖解除
顺序铁律：S1–S4 全部完成、失败分桶显示剩余失败集中在「判断失败」轴之后，才启动 SFT 数据生产。反过来（先 SFT 后改协议）= 数据返工。

11. 落地顺序与回滚

阶段动作验证标准回滚方式
S1（P0）schema v2 定稿 + grammar/validator 同源生成 + few-shot 模板 v1评测集 v0 格式率 ≥ 99%v1 codec case 并存，flag 切换
S2（P0）评测集 v1 构建 + 失败分桶面板上线（与 retry-rate 同面板）全 intent 覆盖、固定 seed、git 版本化—
S3（P1）两阶段拆分实验按 §9 决策规则单阶段路径保留
S4（P1）按分桶 top 桶补边界对 / 修订枚举目标桶占比下降 + 全量复测不回退few-shot 是配置，即时回退
S5（P2+）nlu_10 LoRA SFT（schema 已定稿）acc 门槛建立在 v2 基线上LoRA 独立加载路径

每步独立可回滚；S1/S2 是纯工程无训练成本，本周即可启动。

12. 附录

12.1 与 V3 既有设计的关系

  • 本方案不改变 V3 的管线骨架（BuildRequest → 模型 → ParseResponse → 候选门 → retry）——只填 P0-1（生成侧约束）的 schema 侧内容和失败分桶的观测闭环；
  • 「codec + 显式 factory case」边界保留（Rule of three）：v2 仍是 nlu_10 单协议演进，不引入通用协议注册框架；
  • 采样参数（temperature ≤ 0.2）走 Profile 下发，与 schema 解耦。

12.2 观测面板字段（与健康指标对齐）

格式遵守率 / retry-rate / 失败分桶六桶计数 / unknown 占比 / 长尾切片 acc——同一面板，schema 调优的每次迭代都能在面板上读到因果。
